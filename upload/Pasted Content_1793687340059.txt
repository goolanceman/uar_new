# PHASE 1 — APPLICATION AUDIT AND AUTHENTICATION FIX

## 1. Fix the Admin Authentication Issue First

Currently, when I log in to the admin pages:

- The application says "Please sign in."
- Admin data is not displayed.
- The session appears to be lost or not recognized.
- Some admin pages may redirect to the login page even after successful authentication.

Investigate and fix this issue before beginning the major redesign.

Review:

- Authentication implementation.
- Login API and response structure.
- Session management.
- JWT generation and validation.
- Access token and refresh token handling.
- Cookie configuration.
- Cookie domain, path, SameSite, Secure, and HttpOnly settings.
- CORS configuration.
- API interceptors.
- Authentication middleware.
- Protected routes.
- Admin authorization and role permissions.
- User context and authentication state.
- Server-side rendering authentication.
- Client-side hydration.
- API request headers.
- Data fetching and caching.
- Logout and session expiration.
- Refresh token rotation.
- API response handling.
- Backend authorization.
- Frontend route guards.

Identify the exact root cause.

Do not simply hide the "Please sign in" message or bypass authentication.

Implement a secure and reliable authentication flow.

### Expected authentication behavior

1. Admin logs in successfully.
2. Authentication state is established correctly.
3. The admin dashboard loads without asking the user to sign in again.
4. Admin data is fetched and displayed.
5. Refreshing the browser does not unexpectedly log out the user.
6. Protected routes remain protected.
7. Expired sessions are handled gracefully.
8. Unauthorized users cannot access admin APIs.
9. Login, logout, session restoration, and token refresh work correctly.
10. No infinite redirects or repeated login prompts.

Add proper loading states, error states, session-expired dialogs, and retry behavior.

Create automated tests for authentication and protected routes.

# PHASE 16 — DELETE AND DESTRUCTIVE ACTIONS

Every delete action must have a proper confirmation dialog.

Do not use browser-native confirm() dialogs.

The confirmation should show:

- Record name.
- Record type.
- Consequences.
- Whether deletion is permanent.
- Related records that may be affected.
- Cancel action.
- Confirm action.

For critical records, require typing the record name or an additional confirmation.

Prefer archival or soft deletion where appropriate.

Never allow deletion of financial transactions in a way that destroys audit history.

Use cancellation, correction, or reversal workflows for financial records.
